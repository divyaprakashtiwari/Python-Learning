Question 1 (Easy):
--------------------------------------------------------------------------------
Problem Statement:
Write a Python program that designs a robust mathematical input evaluator `safe_compute_ratio(numerator_str: str, denominator_str: str) -> dict`
demonstrating elementary `try...except` handling and targeted exception capture:
1. Parsing & Computation Logic:
   - Within a `try` block:
     * Convert `numerator_str` to `float`.
     * Convert `denominator_str` to `float`.
     * Compute `ratio = numerator / denominator`.
     * Return `{"status": "SUCCESS", "ratio": round(ratio, 4)}`.
2. Targeted Exception Handlers:
   - Handle string conversion failures with a dedicated `except ValueError as err:` block:
     * Return `{"status": "ERROR", "error_type": "ValueError", "message": str(err)}`.
   - Handle zero division with a dedicated `except ZeroDivisionError as err:` block:
     * Return `{"status": "ERROR", "error_type": "ZeroDivisionError", "message": "Denominator cannot be zero"}`.
3. Clean Exception Trapping:
   - Ensure the function never raises unhandled exceptions to the caller during normal parsing or calculation,
     returning a structured diagnostic dictionary instead.

Sample Input:
test1 = safe_compute_ratio("100", "4")
test2 = safe_compute_ratio("75.5", "0")
test3 = safe_compute_ratio("abc", "10")
test4 = safe_compute_ratio("22", "7")

Expected Output:
Test 1 (100 / 4):
{'status': 'SUCCESS', 'ratio': 25.0}

Test 2 (75.5 / 0):
{'status': 'ERROR', 'error_type': 'ZeroDivisionError', 'message': 'Denominator cannot be zero'}

Test 3 ('abc' / 10):
{'status': 'ERROR', 'error_type': 'ValueError', 'message': "could not convert string to float: 'abc'"}

Test 4 (22 / 7):
{'status': 'SUCCESS', 'ratio': 3.1429}

Constraints & Edge Cases:
- Do not use a bare `except:` or catch universal `Exception` here; handlers must target `ValueError` and `ZeroDivisionError` specifically.
- Leading or trailing whitespace in numeric strings (e.g., `" 42 "`) should parse successfully as standard Python `float()` permits.

Question 2 (Easy-Intermediate):
--------------------------------------------------------------------------------
Problem Statement:
Write a Python program that designs a safe nested data extractor `safe_nested_lookup(data_structure: object, query_path: list, fallback: object = None) -> dict`
demonstrating multiple exception handlers, exception grouping via tuples, and inheritance hierarchy ordering:
1. Traversal Flow:
   - Successively traverses nested dictionaries, lists, and tuples following the elements in `query_path`.
   - Returns the targeted deep value if all keys/indices exist.
2. Multiple Distinct Exception Handlers:
   - Specific Handler for `KeyError`:
     * Triggered when a key is absent from a dictionary.
     * Records failure diagnostic: `"Key '<key>' not found in mapping"`.
   - Specific Handler for `IndexError`:
     * Triggered when an integer index is out of bounds for a sequence.
     * Records failure diagnostic: `"Index <idx> out of range for sequence"`.
   - Combined Group Handler for `(TypeError, AttributeError)`:
     * Triggered when attempting to index a non-subscriptable object (e.g., int, float, None)
       or passing a string index to a list.
     * Records failure diagnostic: `"Invalid subscript access on non-container or wrong key type"`.
3. Hierarchy Ordering Rule:
   - Note that both `KeyError` and `IndexError` inherit from `LookupError`. Demonstrate that
     specific subclass handlers must precede any broader `LookupError` handler to prevent shadowing.
4. Output Schema:
   - On success: returns `{"status": "SUCCESS", "value": val, "depth": len(query_path)}`.
   - On failure: returns `{"status": "FALLBACK", "value": fallback, "error_type": exc.__class__.__name__, "failing_token": key, "diagnostic": msg}`.

Sample Input:
payload = {
    "users": [
        {"id": 101, "profile": {"name": "Alice", "tags": ["admin", "dev"]}},
        {"id": 102, "profile": {"name": "Bob", "tags": []}}
    ]
}

res1 = safe_nested_lookup(payload, ["users", 0, "profile", "name"])
res2 = safe_nested_lookup(payload, ["users", 0, "profile", "email"], fallback="no-email")
res3 = safe_nested_lookup(payload, ["users", 5, "profile"])
res4 = safe_nested_lookup(payload, ["users", 0, "profile", "name", 100])

Expected Output:
Lookup 1 (Valid Path):
{'status': 'SUCCESS', 'value': 'Alice', 'depth': 4}

Lookup 2 (Missing Dict Key 'email'):
{'status': 'FALLBACK', 'value': 'no-email', 'error_type': 'KeyError', 'failing_token': 'email', 'diagnostic': "Key 'email' not found in mapping"}

Lookup 3 (Out of Bounds Index 5):
{'status': 'FALLBACK', 'value': None, 'error_type': 'IndexError', 'failing_token': 5, 'diagnostic': 'Index 5 out of range for sequence'}

Lookup 4 (String Indexing Out of Range):
{'status': 'FALLBACK', 'value': None, 'error_type': 'IndexError', 'failing_token': 100, 'diagnostic': 'Index 100 out of range for sequence'}

Lookup 5 (Indexing into Non-Container None):
safe_nested_lookup(None, ["users"]) -> 'TypeError' caught by (TypeError, AttributeError) group.

Constraints & Edge Cases:
- Empty `query_path` should return `{"status": "SUCCESS", "value": data_structure, "depth": 0}`.
- Specific exception handlers must strictly appear before any general superclass handlers in the code structure.

Question 3 (Easy-Intermediate):
--------------------------------------------------------------------------------
Problem Statement:
Write a Python program that designs a simulated transactional database executor
`execute_transaction(conn_pool: dict, queries: list[str], fail_on_query_index: int = -1) -> dict`
demonstrating the complete, precise lifecycle of `try`, `except`, `else`, and `finally` clauses:
1. Lifecycle Execution Contract:
   - `try`:
     * Checks out an active database connection token (e.g. marks `conn_pool["status"] = "BUSY"`).
     * Iterates through `queries`. If current index == `fail_on_query_index`, raises `RuntimeError(f"Query '{queries[index]}' execution failed")`.
     * Accumulates successfully executed query names in a staging list.
   - `except RuntimeError as err`:
     * Executes ONLY if an error occurred during execution.
     * Records rollback event (`conn_pool["rollbacks"] += 1`) and logs failure message.
     * Prepares failure response record.
   - `else`:
     * Executes ONLY if the `try` block ran to completion with ZERO exceptions.
     * Commits transaction (`conn_pool["commits"] += 1`).
     * Prepares success response record containing all committed queries.
   - `finally`:
     * ALWAYS executes without exception, regardless of whether `try` succeeded, an error was caught,
       or an unexpected exception occurred.
     * Guarantees releasing the connection back to idle state (`conn_pool["status"] = "IDLE"`).
     * Records cleanup timestamp and increments `conn_pool["total_transactions"] += 1`.
2. Return Override Caveat Demonstration:
   - Include a code snippet / explanation demonstrating why placing an explicit `return` or `break`
     inside a `finally` block is dangerous (it silences any active exceptions and overrides prior returns).

Sample Input:
pool = {"status": "IDLE", "commits": 0, "rollbacks": 0, "total_transactions": 0}
queries_batch = ["SELECT * FROM users", "UPDATE users SET active=1", "INSERT INTO audit_log VALUES (1)"]

# Case A: Successful Execution (exercises try -> else -> finally)
res_success = execute_transaction(pool, queries_batch, fail_on_query_index=-1)

# Case B: Execution with Failure (exercises try -> except -> finally)
res_failure = execute_transaction(pool, queries_batch, fail_on_query_index=1)

Expected Output:
Case A (Success):
- Result: {'status': 'COMMITTED', 'queries_run': 3}
- Pool State: {'status': 'IDLE', 'commits': 1, 'rollbacks': 0, 'total_transactions': 1}

Case B (Failure on query index 1):
- Result: {'status': 'ROLLED_BACK', 'failed_query': 'UPDATE users SET active=1', 'error': "Query 'UPDATE users SET active=1' execution failed"}
- Pool State: {'status': 'IDLE', 'commits': 1, 'rollbacks': 1, 'total_transactions': 2}

Lifecycle Verification:
In Case A: `else` ran (commit executed), `except` was bypassed, `finally` released connection.
In Case B: `except` ran (rollback executed), `else` was bypassed, `finally` released connection.

Constraints & Edge Cases:
- The connection must be returned to `"IDLE"` in `finally` even if `queries` contains invalid data types.
- The `else` block must never execute if an exception was raised and caught in `try`.
