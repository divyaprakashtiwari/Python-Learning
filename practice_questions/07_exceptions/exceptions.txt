Question 1 (Easy):
--------------------------------------------------------------------------------
Problem Statement:
Write a Python program that designs a robust mathematical input evaluator `safe_compute_ratio(numerator_str: str, denominator_str: str) -> dict`
demonstrating elementary `try...except` handling and targeted exception capture:
1. Parsing & Computation Logic:
   - Within a `try` block:
     * Convert `numerator_str` to `float`.
     * Convert `denominator_str` to `float`.
     * Compute `ratio = numerator / denominator`.
     * Return `{"status": "SUCCESS", "ratio": round(ratio, 4)}`.
2. Targeted Exception Handlers:
   - Handle string conversion failures with a dedicated `except ValueError as err:` block:
     * Return `{"status": "ERROR", "error_type": "ValueError", "message": str(err)}`.
   - Handle zero division with a dedicated `except ZeroDivisionError as err:` block:
     * Return `{"status": "ERROR", "error_type": "ZeroDivisionError", "message": "Denominator cannot be zero"}`.
3. Clean Exception Trapping:
   - Ensure the function never raises unhandled exceptions to the caller during normal parsing or calculation,
     returning a structured diagnostic dictionary instead.

Sample Input:
test1 = safe_compute_ratio("100", "4")
test2 = safe_compute_ratio("75.5", "0")
test3 = safe_compute_ratio("abc", "10")
test4 = safe_compute_ratio("22", "7")

Expected Output:
Test 1 (100 / 4):
{'status': 'SUCCESS', 'ratio': 25.0}

Test 2 (75.5 / 0):
{'status': 'ERROR', 'error_type': 'ZeroDivisionError', 'message': 'Denominator cannot be zero'}

Test 3 ('abc' / 10):
{'status': 'ERROR', 'error_type': 'ValueError', 'message': "could not convert string to float: 'abc'"}

Test 4 (22 / 7):
{'status': 'SUCCESS', 'ratio': 3.1429}

Constraints & Edge Cases:
- Do not use a bare `except:` or catch universal `Exception` here; handlers must target `ValueError` and `ZeroDivisionError` specifically.
- Leading or trailing whitespace in numeric strings (e.g., `" 42 "`) should parse successfully as standard Python `float()` permits.

Question 2 (Easy-Intermediate):
--------------------------------------------------------------------------------
Problem Statement:
Write a Python program that designs a safe nested data extractor `safe_nested_lookup(data_structure: object, query_path: list, fallback: object = None) -> dict`
demonstrating multiple exception handlers, exception grouping via tuples, and inheritance hierarchy ordering:
1. Traversal Flow:
   - Successively traverses nested dictionaries, lists, and tuples following the elements in `query_path`.
   - Returns the targeted deep value if all keys/indices exist.
2. Multiple Distinct Exception Handlers:
   - Specific Handler for `KeyError`:
     * Triggered when a key is absent from a dictionary.
     * Records failure diagnostic: `"Key '<key>' not found in mapping"`.
   - Specific Handler for `IndexError`:
     * Triggered when an integer index is out of bounds for a sequence.
     * Records failure diagnostic: `"Index <idx> out of range for sequence"`.
   - Combined Group Handler for `(TypeError, AttributeError)`:
     * Triggered when attempting to index a non-subscriptable object (e.g., int, float, None)
       or passing a string index to a list.
     * Records failure diagnostic: `"Invalid subscript access on non-container or wrong key type"`.
3. Hierarchy Ordering Rule:
   - Note that both `KeyError` and `IndexError` inherit from `LookupError`. Demonstrate that
     specific subclass handlers must precede any broader `LookupError` handler to prevent shadowing.
4. Output Schema:
   - On success: returns `{"status": "SUCCESS", "value": val, "depth": len(query_path)}`.
   - On failure: returns `{"status": "FALLBACK", "value": fallback, "error_type": exc.__class__.__name__, "failing_token": key, "diagnostic": msg}`.

Sample Input:
payload = {
    "users": [
        {"id": 101, "profile": {"name": "Alice", "tags": ["admin", "dev"]}},
        {"id": 102, "profile": {"name": "Bob", "tags": []}}
    ]
}

res1 = safe_nested_lookup(payload, ["users", 0, "profile", "name"])
res2 = safe_nested_lookup(payload, ["users", 0, "profile", "email"], fallback="no-email")
res3 = safe_nested_lookup(payload, ["users", 5, "profile"])
res4 = safe_nested_lookup(payload, ["users", 0, "profile", "name", 100])

Expected Output:
Lookup 1 (Valid Path):
{'status': 'SUCCESS', 'value': 'Alice', 'depth': 4}

Lookup 2 (Missing Dict Key 'email'):
{'status': 'FALLBACK', 'value': 'no-email', 'error_type': 'KeyError', 'failing_token': 'email', 'diagnostic': "Key 'email' not found in mapping"}

Lookup 3 (Out of Bounds Index 5):
{'status': 'FALLBACK', 'value': None, 'error_type': 'IndexError', 'failing_token': 5, 'diagnostic': 'Index 5 out of range for sequence'}

Lookup 4 (String Indexing Out of Range):
{'status': 'FALLBACK', 'value': None, 'error_type': 'IndexError', 'failing_token': 100, 'diagnostic': 'Index 100 out of range for sequence'}

Lookup 5 (Indexing into Non-Container None):
safe_nested_lookup(None, ["users"]) -> 'TypeError' caught by (TypeError, AttributeError) group.

Constraints & Edge Cases:
- Empty `query_path` should return `{"status": "SUCCESS", "value": data_structure, "depth": 0}`.
- Specific exception handlers must strictly appear before any general superclass handlers in the code structure.

Question 3 (Easy-Intermediate):
--------------------------------------------------------------------------------
Problem Statement:
Write a Python program that designs a simulated transactional database executor
`execute_transaction(conn_pool: dict, queries: list[str], fail_on_query_index: int = -1) -> dict`
demonstrating the complete, precise lifecycle of `try`, `except`, `else`, and `finally` clauses:
1. Lifecycle Execution Contract:
   - `try`:
     * Checks out an active database connection token (e.g. marks `conn_pool["status"] = "BUSY"`).
     * Iterates through `queries`. If current index == `fail_on_query_index`, raises `RuntimeError(f"Query '{queries[index]}' execution failed")`.
     * Accumulates successfully executed query names in a staging list.
   - `except RuntimeError as err`:
     * Executes ONLY if an error occurred during execution.
     * Records rollback event (`conn_pool["rollbacks"] += 1`) and logs failure message.
     * Prepares failure response record.
   - `else`:
     * Executes ONLY if the `try` block ran to completion with ZERO exceptions.
     * Commits transaction (`conn_pool["commits"] += 1`).
     * Prepares success response record containing all committed queries.
   - `finally`:
     * ALWAYS executes without exception, regardless of whether `try` succeeded, an error was caught,
       or an unexpected exception occurred.
     * Guarantees releasing the connection back to idle state (`conn_pool["status"] = "IDLE"`).
     * Records cleanup timestamp and increments `conn_pool["total_transactions"] += 1`.
2. Return Override Caveat Demonstration:
   - Include a code snippet / explanation demonstrating why placing an explicit `return` or `break`
     inside a `finally` block is dangerous (it silences any active exceptions and overrides prior returns).

Sample Input:
pool = {"status": "IDLE", "commits": 0, "rollbacks": 0, "total_transactions": 0}
queries_batch = ["SELECT * FROM users", "UPDATE users SET active=1", "INSERT INTO audit_log VALUES (1)"]

# Case A: Successful Execution (exercises try -> else -> finally)
res_success = execute_transaction(pool, queries_batch, fail_on_query_index=-1)

# Case B: Execution with Failure (exercises try -> except -> finally)
res_failure = execute_transaction(pool, queries_batch, fail_on_query_index=1)

Expected Output:
Case A (Success):
- Result: {'status': 'COMMITTED', 'queries_run': 3}
- Pool State: {'status': 'IDLE', 'commits': 1, 'rollbacks': 0, 'total_transactions': 1}

Case B (Failure on query index 1):
- Result: {'status': 'ROLLED_BACK', 'failed_query': 'UPDATE users SET active=1', 'error': "Query 'UPDATE users SET active=1' execution failed"}
- Pool State: {'status': 'IDLE', 'commits': 1, 'rollbacks': 1, 'total_transactions': 2}

Lifecycle Verification:
In Case A: `else` ran (commit executed), `except` was bypassed, `finally` released connection.
In Case B: `except` ran (rollback executed), `else` was bypassed, `finally` released connection.

Constraints & Edge Cases:
- The connection must be returned to `"IDLE"` in `finally` even if `queries` contains invalid data types.
- The `else` block must never execute if an exception was raised and caught in `try`.

Question 4 (Easy-Intermediate):
--------------------------------------------------------------------------------
Problem Statement:
Write a Python program that designs an identity registration gatekeeper `register_account(profile: dict) -> dict`
and an auditing middleware `audit_registration_wrapper(profile: dict, audit_log: list) -> dict`
demonstrating explicit exception raising, condition-based validation, and bare `raise` re-raising:
1. Defensive Validation & Explicit `raise`:
   - `register_account(profile: dict) -> dict`:
     * Required Keys: Check presence of `"username"`, `"email"`, `"age"`, and `"role"`.
       If any key is missing, explicitly `raise KeyError(f"Missing mandatory registration field: '{key}'")`.
     * Type Validation: If `profile["age"]` is not an integer, `raise TypeError("Age must be an integer")`.
     * Value Boundaries:
       - If `age < 18` or `age > 120`: `raise ValueError(f"Age {age} is outside permitted registration bounds (18-120)")`.
       - If `"@" not in profile["email"]` or `"." not in profile["email"]`: `raise ValueError("Invalid email format")`.
       - If `profile["role"]` not in `{"STANDARD", "OPERATOR", "ADMIN"}`: `raise ValueError(f"Unauthorized role: '{profile['role']}'")`.
     * On successful validation: returns `{"account_id": f"ACC-{hash(profile['username']) % 10000:04d}", "status": "REGISTERED"}`.
2. Interception and Bare Re-Raise (`raise` without expression):
   - `audit_registration_wrapper(profile: dict, audit_log: list) -> dict`:
     * In the `try` block, invoke `register_account(profile)`.
     * In an `except Exception as err:` block:
       - Append diagnostic failure event to `audit_log`: `{"event": "REGISTRATION_FAILED", "error": type(err).__name__, "message": str(err)}`.
       - Use a bare `raise` statement to re-raise the exact active exception, preserving the original
         stack trace and exception type for upstream callers.

Sample Input:
audit_trail = []

# Test A: Valid User
valid_user = {"username": "jdoe", "email": "jdoe@company.org", "age": 28, "role": "STANDARD"}
acc = audit_registration_wrapper(valid_user, audit_trail)

# Test B: Underage User (raises ValueError)
underage_user = {"username": "kid99", "email": "kid@fun.org", "age": 16, "role": "STANDARD"}
try:
    audit_registration_wrapper(underage_user, audit_trail)
except ValueError as exc:
    print("Caught Upstream Error:", exc)

# Test C: Missing Key (raises KeyError)
missing_key_user = {"username": "anon", "email": "anon@test.io", "age": 30}
try:
    audit_registration_wrapper(missing_key_user, audit_trail)
except KeyError as exc:
    print("Caught Upstream Error:", exc)

Expected Output:
Registration Success: Account Created ACC-1234
Caught Upstream Error: Age 16 is outside permitted registration bounds (18-120)
Caught Upstream Error: 'Missing mandatory registration field: \'role\''

Audit Trail Entries (2 logged failures):
1. Event: REGISTRATION_FAILED | Error: ValueError | Message: Age 16 is outside permitted registration bounds (18-120)
2. Event: REGISTRATION_FAILED | Error: KeyError | Message: 'Missing mandatory registration field: \'role\''

Constraints & Edge Cases:
- Never use `raise Exception(...)`; always raise the most semantically appropriate built-in type (`KeyError`, `ValueError`, `TypeError`).
- Re-raising must use the bare `raise` syntax to avoid altering the exception's original frame traceback.

Problem Statement:
Write a Python program that designs a domain-specific custom exception hierarchy for a fintech
transaction processor `PaymentProcessor` to provide rich error metadata, status codes, and user-friendly diagnostics:
1. Base Domain Exception `PaymentGatewayError(Exception)`:
   - `__init__(self, message: str, error_code: str, transaction_id: str)`:
     * Stores attributes `message`, `error_code`, `transaction_id`.
     * Overrides `__str__(self) -> str`: returns `f"[{self.error_code}] Tx '{self.transaction_id}': {self.message}"`.
2. Specialized Subclasses:
   - `InsufficientFundsError(PaymentGatewayError)`:
     * `__init__(self, transaction_id: str, available_balance: float, attempted_amount: float)`:
       Stores `available_balance`, `attempted_amount`.
       Computes `shortfall = attempted_amount - available_balance`.
       Calls `super().__init__(message=f"Insufficient funds: Shortfall of ${shortfall:.2f}", error_code="ERR_INSUFFICIENT_FUNDS", transaction_id=transaction_id)`.
   - `CardExpiredError(PaymentGatewayError)`:
     * `__init__(self, transaction_id: str, card_last4: str, expiry_date: str)`:
       Stores `card_last4`, `expiry_date`.
       Calls `super().__init__(message=f"Card ending in {card_last4} expired on {expiry_date}", error_code="ERR_CARD_EXPIRED", transaction_id=transaction_id)`.
   - `FraudRiskBlockError(PaymentGatewayError)`:
     * `__init__(self, transaction_id: str, risk_score: float)`:
       Stores `risk_score`.
       Calls `super().__init__(message=f"Transaction blocked due to elevated fraud score ({risk_score:.2f} > 0.85)", error_code="ERR_FRAUD_TRIGGERED", transaction_id=transaction_id)`.
3. Settlement Engine:
   - `process_charge(tx_id: str, card: dict, balance: float, charge_amount: float) -> dict`:
     * If `card.get("risk_score", 0.0) > 0.85`: `raise FraudRiskBlockError(tx_id, card["risk_score"])`.
     * If `card.get("is_expired", False)`: `raise CardExpiredError(tx_id, card["last4"], card["expiry"])`.
     * If `balance < charge_amount`: `raise InsufficientFundsError(tx_id, balance, charge_amount)`.
     * If all checks pass: returns `{"tx_id": tx_id, "status": "APPROVED", "new_balance": balance - charge_amount}`.
4. Polymorphic Exception Catching:
   - Show that a generic client can catch `PaymentGatewayError` and extract `.error_code`, `.transaction_id`
     without knowing the specific child class, while an advanced caller can catch `InsufficientFundsError`
     to access `.shortfall`.

Sample Input:
card_ok = {"last4": "4242", "expiry": "12/28", "is_expired": False, "risk_score": 0.12}
card_exp = {"last4": "1111", "expiry": "01/22", "is_expired": True, "risk_score": 0.05}
card_fraud = {"last4": "9999", "expiry": "05/27", "is_expired": False, "risk_score": 0.94}

# Test 1: Low balance
try:
    process_charge("TX-1001", card_ok, balance=50.0, charge_amount=120.0)
except InsufficientFundsError as err:
    print("Caught Specific:", err)
    print("Actionable Metadata: Shortfall =", err.shortfall)

# Test 2: Expired card caught via generic base exception
try:
    process_charge("TX-1002", card_exp, balance=500.0, charge_amount=20.0)
except PaymentGatewayError as err:
    print("Caught via Base:", err.error_code, "|", err)

Expected Output:
Caught Specific: [ERR_INSUFFICIENT_FUNDS] Tx 'TX-1001': Insufficient funds: Shortfall of $70.00
Actionable Metadata: Shortfall = 70.0
Caught via Base: ERR_CARD_EXPIRED | [ERR_CARD_EXPIRED] Tx 'TX-1002': Card ending in 1111 expired on 01/22

Constraints & Edge Cases:
- All custom exception classes must inherit from `PaymentGatewayError` which itself inherits from built-in `Exception` (never `BaseException`).
- All numeric currency fields must format cleanly with 2 decimal places.

Problem Statement:
Write a Python program that designs a microservice secret and configuration manager
`ServiceConfigLoader` demonstrating explicit exception chaining (`raise ... from orig`),
traceback context suppression (`raise ... from None`), and introspection of `__cause__` and `__context__`:
1. Custom Domain Exceptions:
   - `ConfigurationLoadError(Exception)`: General configuration parsing failure.
   - `InvalidSecurityTokenError(Exception)`: Security credential token failure.
2. Explicit Chaining with `raise ... from orig_err`:
   - `load_cluster_settings(filepath: str) -> dict`:
     * Attempts to open and read `filepath`.
     * Catches `FileNotFoundError` as `err`:
       `raise ConfigurationLoadError(f"Cluster config file '{filepath}' is missing") from err`.
     * Explicitly preserves the root cause, causing Python to link `new_exc.__cause__ = err`
       and display `"The above exception was the direct cause of the following exception:"`.
3. Context Suppression with `raise ... from None`:
   - `decode_api_bearer_token(raw_token: str) -> dict`:
     * Attempts to base64-decode and parse `raw_token`.
     * If `binascii.Error` or `UnicodeDecodeError` or `ValueError` occurs:
       `raise InvalidSecurityTokenError("Bearer token is malformed or signature corrupted") from None`.
     * Setting `from None` sets `new_exc.__cause__ = None` and `new_exc.__suppress_context__ = True`,
       intentionally suppressing internal low-level implementation details and cryptographic libraries

4. Introspection Utility:
   - `inspect_chaining(exc: BaseException) -> dict`:

- Suppress Context: False

Chaining Info (Test 2 - Suppressed Context):
- Exception: InvalidSecurityTokenError
- Message: Bearer token is malformed or signature corrupted
- Cause: None

Constraints & Edge Cases:
- Never let low-level internal decoding traces leak to users when processing sensitive authentication tokens.
- Explicit chaining must retain full access to `err.__cause__` for internal SRE logging and root cause analysis.

Question 7 (Intermediate):
--------------------------------------------------------------------------------
Problem Statement:
Write a Python program that designs a configurable, resilient execution context manager
`FaultTolerantScope` that inspects exception details in `__exit__` and selectively suppresses
or propagates errors based on configured rules:
1. Context Manager Protocol:
   - `__init__(self, suppress_types: tuple[type[BaseException], ...], on_suppress_hook: Callable = None)`:
     * Stores allowed suppressible exception classes.
     * Stores optional callback invoked whenever an exception is caught and suppressed.
     * Sets internal state: `self.suppressed_exception = None`, `self.was_suppressed = False`.
   - `__enter__(self) -> "FaultTolerantScope"`:
     * Returns `self`.
   - `__exit__(self, exc_type, exc_val, exc_tb) -> bool`:
     * If `exc_type is None`: no exception occurred; returns `False`.
     * Check type membership: if `issubclass(exc_type, self.suppress_types)`:
       - Records `self.suppressed_exception = exc_val` and `self.was_suppressed = True`.
       - If `on_suppress_hook` is callable, calls `on_suppress_hook(exc_val)`.
       - Returns `True` (instructing the Python runtime to swallow the exception and resume normal execution after the `with` block).
     * If `exc_type` is NOT a subclass of `suppress_types`:
       - Returns `False` (allowing the exception to propagate naturally up the call stack).
2. Diagnostic Execution Testing:
   - Test Case A: Suppressed `KeyError` within scope. Execution continues past the block.
   - Test Case B: Suppressed `ZeroDivisionError` with a custom telemetry callback.
   - Test Case C: Non-suppressed `TypeError` correctly escapes the scope and triggers an outer `try...except`.

Sample Input:
suppressed_events = []
def record_event(err):
    suppressed_events.append(f"Handled {type(err).__name__}: {err}")

# Test 1: Suppressing KeyError
with FaultTolerantScope(suppress_types=(KeyError,), on_suppress_hook=record_event) as scope1:
    data = {"a": 1}
    val = data["missing_key"]
print("Continued after Scope 1. Suppressed?", scope1.was_suppressed)

# Test 2: Unhandled TypeError escapes
try:
    with FaultTolerantScope(suppress_types=(ValueError,)):
        num = int("123")
        res = "abc" + 10  # Raises TypeError
except TypeError as unhandled:
    print("Caught unhandled escaping error:", unhandled)

Expected Output:
Continued after Scope 1. Suppressed? True
Suppressed Events: ["Handled KeyError: 'missing_key'"]
Caught unhandled escaping error: can only concatenate str (not "int") to str

Constraints & Edge Cases:
- Never suppress `KeyboardInterrupt` or `SystemExit` even if the user passes broad base exceptions.
- The `__exit__` method must explicitly return a boolean (`True` to suppress, `False` to propagate).
