Question 1 (Easy):
--------------------------------------------------------------------------------
Problem Statement:
Write a Python program that designs a domain model `BankAccount` and builds an automated unit test suite using standard library `unittest`:
1. Domain Model Specification (`BankAccount`):
   - `__init__(account_holder: str, initial_balance: float = 0.0)`: Initializes account; raises `ValueError` if `initial_balance < 0`.
   - `deposit(amount: float) -> float`: Adds amount to balance and returns new balance; raises `ValueError` if `amount <= 0`.
   - `withdraw(amount: float) -> float`: Subtracts amount from balance and returns new balance; raises `ValueError` if `amount <= 0`, or raises custom `InsufficientFundsError` if `amount > balance`.
   - `balance`: Read-only property returning current funds.
2. Test Suite Implementation (`TestBankAccount(unittest.TestCase)`):
   - Test method `test_initial_balance_valid`: Asserts balance equals initialized amount.
   - Test method `test_initial_balance_negative`: Uses `assertRaises(ValueError)` to verify negative initial deposits fail.
   - Test method `test_deposit_success`: Verifies balance increments correctly after multiple deposits.
   - Test method `test_deposit_invalid_amount`: Asserts zero or negative deposit raises `ValueError`.
   - Test method `test_withdraw_success`: Asserts withdrawal decrements balance accurately.
   - Test method `test_withdraw_insufficient_funds`: Asserts `InsufficientFundsError` is raised when overdrawing.
3. Programmatic Test Runner:
   - Loads test cases via `unittest.TestLoader().loadTestsFromTestCase(...)`.
   - Executes tests using `unittest.TextTestRunner(verbosity=2)`.
   - Programmatically inspects the `TestResult` object: verifies `testsRun`, `failures`, `errors`, and `wasSuccessful()`.

Sample Input:
# Programmatic test execution
suite = unittest.TestLoader().loadTestsFromTestCase(TestBankAccount)
runner = unittest.TextTestRunner(verbosity=0)
result = runner.run(suite)

# Inspect outcomes
total_ran = result.testsRun
was_success = result.wasSuccessful()
fail_count = len(result.failures)
err_count = len(result.errors)

Expected Output:
Tests Run: 6
All Tests Passed: True
Failures Count: 0
Errors Count: 0
Execution Status: SUCCESS

Constraints & Edge Cases:
- Floating point balance operations must be tested using `assertAlmostEqual(actual, expected, places=2)` to prevent IEEE-754 precision mismatches.
- Tests must be completely self-contained; test execution order must not affect outcomes.

Question 2 (Easy-Intermediate):
--------------------------------------------------------------------------------
Problem Statement:
Write a Python program that designs a File-Backed Cache Manager `PersistentFileCache` and constructs a comprehensive test fixture harness demonstrating `setUp`, `tearDown`, `setUpClass`, `tearDownClass`, and `addCleanup`:
1. System Under Test (`PersistentFileCache`):
   - `__init__(cache_dir: str)`: Creates directory if non-existent.
   - `set(key: str, data: dict[str, Any], ttl_seconds: float = 3600.0) -> None`: Serializes dictionary to `<cache_dir>/<key>.json` with expiration timestamp metadata.
   - `get(key: str) -> Optional[dict[str, Any]]`: Reads cached JSON; returns `None` if absent or if expired (deleting stale file upon detection).
   - `delete(key: str) -> bool`: Removes cache file; returns `True` if existed.
   - `clear() -> int`: Cleans all entries in cache directory and returns count of purged entries.
2. Fixture Lifecycle Architecture (`TestPersistentFileCache(unittest.TestCase)`):
   - `setUpClass(cls)`:
     * Creates an isolated temporary directory via `tempfile.mkdtemp(prefix="cache_test_")`.
     * Instantiates shared cache manager.
   - `tearDownClass(cls)`:
     * Recursively purges temporary directory via `shutil.rmtree` to avoid leaving orphaned test files on disk.
   - `setUp(self)`:
     * Seeds fresh baseline test entries: `cache.set("session_user", {"id": 1, "name": "Alice"})`.
   - `tearDown(self)`:
     * Calls `cache.clear()` ensuring each test starts with a known, isolated state.
   - Dynamic Cleanup via `self.addCleanup`:
     * In a test creating an explicit lock file, registers an inline cleanup callback to guarantee lock deletion even if an assertion errors midway.

Sample Input:
# Run test suite programmatically
suite = unittest.TestLoader().loadTestsFromTestCase(TestPersistentFileCache)
runner = unittest.TextTestRunner(verbosity=0)
result = runner.run(suite)

# Inspect lifecycle verification
is_successful = result.wasSuccessful()
tests_executed = result.testsRun

Expected Output:
Fixture Lifecycle Tests Run: 5
- test_get_existing_baseline: PASSED
- test_expired_entry_purged: PASSED
- test_cache_delete_removes_file: PASSED
- test_cache_clear_purges_all: PASSED
- test_cleanup_callback_executed: PASSED
All Fixture Tests Passed: True
Temporary Directory Cleared Post-Class: Verified

Constraints & Edge Cases:
- Tests must never pollute repository directories; all files must reside in `tempfile.gettempdir()`.
- Expired entries must be verified with artificial clock manipulation or low TTL (`ttl=0.01`).
- Failure of a single test must not prevent `tearDown` or `tearDownClass` from running.

Question 3 (Easy-Intermediate):
--------------------------------------------------------------------------------
Problem Statement:
Write a Python program that designs an order calculation engine `OrderProcessingEngine` and implements an exhaustive `unittest.TestCase` suite testing boundary conditions with specialized assertions:
1. System Under Test (`OrderProcessingEngine`):
   - Computes line-item totals, applies promotional percentage discounts, taxes, and shipping fees.
   - Raises structured exception `OrderValidationError(field: str, code: str, message: str)` on invalid inputs (e.g. empty line items, negative quantities, discount > 100%).
   - Returns structured dictionary:
     `{"subtotal": float, "discount_amount": float, "tax": float, "shipping": float, "total": float, "applied_promos": list[str]}`.
2. Specialized Assertion Test Harness (`TestOrderProcessingAssertions(unittest.TestCase)`):
   - Floating-Point Tolerance: Uses `assertAlmostEqual(actual, expected, places=2)` and `assertAlmostEqual(actual, expected, delta=0.01)` to test monetary calculations.
   - Unordered Sequence Comparison: Uses `assertCountEqual(actual_promos, expected_promos)` to confirm that applied coupon codes match regardless of generation sequence.
   - Granular Dictionary Difference: Uses `assertDictEqual(actual_summary, expected_summary)` with meaningful diagnostic messages.
   - Identity vs Value Equality: Contrasts `assertIs(obj1, obj2)` with `assertEqual(obj1, obj2)`.
   - Type Membership: Uses `assertIsInstance(result["total"], float)` and `assertIn("TAX_NY_8pct", result["applied_promos"])`.
   - Exception Payload Verification: Uses `with self.assertRaises(OrderValidationError) as ctx:` and verifies that `ctx.exception.field == "discount_pct"` and `ctx.exception.code == "DISCOUNT_OVERFLOW"`.

Sample Input:
# Run test suite programmatically
suite = unittest.TestLoader().loadTestsFromTestCase(TestOrderProcessingAssertions)
runner = unittest.TextTestRunner(verbosity=0)
result = runner.run(suite)

# Inspect outcomes
is_success = result.wasSuccessful()
ran_count = result.testsRun

Expected Output:
Assertions Deep Dive Tests Run: 6
- test_floating_point_tax_precision: PASSED
- test_discount_unordered_coupons: PASSED
- test_dict_summary_equality: PASSED
- test_singleton_sentinel_identity: PASSED
- test_type_and_collection_membership: PASSED
- test_exception_context_payload: PASSED
All Assertion Tests Succeeded: True

Constraints & Edge Cases:
- Never use simple `assertTrue(a == b)` where specialized assertions like `assertEqual` or `assertDictEqual` provide clear visual diffs upon failure.
- Exception verification must assert both exception class and specific attribute values inside the context manager.

Question 4 (Intermediate):
--------------------------------------------------------------------------------
Problem Statement:
Write a Python program that designs an e-commerce Payment Service `CheckoutService` and tests it using `unittest.mock` (`Mock`, `MagicMock`, `@patch`, `side_effect`, `call_args_list`) without making network calls:
1. System Under Test (`CheckoutService`):
   - Dependencies: `PaymentGatewayClient` (remote API) and `EmailNotificationService` (SMTP).
   - Method `process_order(order_id: str, amount: float, customer_email: str) -> dict[str, Any]`:
     * Charges payment gateway: `gateway.charge(amount, currency="USD") -> dict`.
     * If charge succeeds (`status == "COMPLETED"`): sends email receipt via `emailer.send_receipt(to, order_id, amount)` and returns order record.
     * If charge raises `GatewayTimeoutError`: retries up to 2 times before giving up and raising `PaymentFailedError`.
     * If charge fails permanently (e.g. `CardDeclinedError`): does NOT send receipt; raises `PaymentDeclinedError`.
2. Mocking Test Suite (`TestCheckoutServiceMocking(unittest.TestCase)`):
   - Test Method 1 (Happy Path):
     * Mocks `PaymentGatewayClient` and `EmailNotificationService`.
     * Sets `mock_gateway.charge.return_value = {"status": "COMPLETED", "tx_id": "TXN_778"}`.
     * Asserts `mock_gateway.charge.assert_called_once_with(150.0, currency="USD")`.
     * Asserts `mock_emailer.send_receipt.assert_called_once_with("alice@example.com", "ORD_101", 150.0)`.
   - Test Method 2 (Card Declined):
     * Configures `mock_gateway.charge.side_effect = CardDeclinedError("Insufficient funds")`.
     * Asserts `PaymentDeclinedError` is raised.
     * Asserts `mock_emailer.send_receipt.assert_not_called()`.
   - Test Method 3 (Transient Failure with Successful Retry):
     * Configures `side_effect = [GatewayTimeoutError("Timeout"), {"status": "COMPLETED", "tx_id": "TXN_999"}]`.
     * Verifies that `charge` was called exactly twice (`self.assertEqual(mock_gateway.charge.call_count, 2)`).
     * Verifies successful order completion on the second attempt.

Sample Input:
# Programmatic test execution
suite = unittest.TestLoader().loadTestsFromTestCase(TestCheckoutServiceMocking)
runner = unittest.TextTestRunner(verbosity=0)
result = runner.run(suite)

# Inspect test results
is_success = result.wasSuccessful()
tests_ran = result.testsRun

Expected Output:
Mocking Tests Run: 3
- test_payment_success_triggers_receipt: PASSED
- test_card_declined_aborts_without_receipt: PASSED
- test_gateway_timeout_retries_and_succeeds: PASSED
All Mock Tests Passed: True

Constraints & Edge Cases:
- Never patch where an object is defined; patch where it is *imported and looked up* by the consumer module.
- Always clean up patches (via context manager or decorator) to prevent mock leakage across test cases.

Question 5 (Intermediate):
--------------------------------------------------------------------------------
Problem Statement:
Write a Python program that designs a URL Slugifier and Sanitizer `SlugEngine` and constructs a parameterized test suite using `unittest.TestCase.subTest` to evaluate a large test parameter matrix without stopping at first failure:
1. System Under Test (`SlugEngine`):
   - Function `slugify(text: str, max_length: int = 50, separator: str = "-", allow_unicode: bool = False) -> str`:
     * Converts to lowercase and normalizes accented characters (e.g. `é` -> `e`) using `unicodedata.normalize("NFKD")` when `allow_unicode=False`.
     * Strips non-alphanumeric characters (keeping only letters, digits, and whitespace).
     * Collapses consecutive whitespace or separator sequences into a single `separator`.
     * Trims leading and trailing separators.
     * Truncates at word boundaries so words are not sliced in half if length exceeds `max_length`.
     * Raises `ValueError` if `text` is empty or only whitespace.
2. Parameterized Test Suite (`TestSlugEngineParameterized(unittest.TestCase)`):
   - Parameter Matrix for Success Cases:
     * Defines a list of test tuples: `[(raw_input, expected_slug, options_dict), ...]`.
     * Tests standard strings, accented letters, punctuation overload, max-length boundary truncations, and custom separators.
     * Iterates through matrix using `with self.subTest(input=raw_input, expected=expected_slug):`.
     * Asserts that `slugify(raw_input, **options_dict) == expected_slug`.
   - Parameter Matrix for Exception Cases:
     * Tests whitespace-only, empty strings, and negative lengths.
     * Iterates using `with self.subTest(invalid_input=val):` asserting `assertRaises(ValueError)`.
3. Diagnostic Capability:
   - Demonstrates that if one test matrix row encounters an assertion failure, subsequent `subTest` iterations still execute to completion and isolate the exact failing parameters in the runner report.

Sample Input:
# Programmatic test execution
suite = unittest.TestLoader().loadTestsFromTestCase(TestSlugEngineParameterized)
runner = unittest.TextTestRunner(verbosity=0)
result = runner.run(suite)

# Inspect subtest reporting
is_success = result.wasSuccessful()
tests_ran = result.testsRun

Expected Output:
Parameterized Test Method Run: 2 (1 for valid matrix with 10 subtests, 1 for invalid matrix with 4 subtests)
Total SubTests Evaluated: 14
SubTest Valid Examples:
- "Hello World!" -> "hello-world"
- "Crème Brûlée & Café" -> "creme-brulee-cafe"
- "Python 3.12: The Next Gen" (max_len=15) -> "python-312-the"
- "Custom___Under__Score" (separator="_") -> "custom_under_score"
All 14 SubTests Passed: True

Constraints & Edge Cases:
- Never use a bare `for` loop without `self.subTest`, as a single failure will abort subsequent test permutations.
- Parameter dictionary passed to `subTest(...)` must clearly identify which row of the test matrix is running.

Question 6 (Intermediate):
--------------------------------------------------------------------------------
Problem Statement:
Write a Python program that designs an automated debugging harness `PdbSessionAutomator` to demonstrate programmatic debugging, command simulation, and post-mortem diagnosis using `pdb`:
1. Buggy Computational Workflow (`calculate_compound_interest`):
   - Computes compound interest over a time series with intentional edge-case logic faults (e.g. division by zero on zero frequency or negative rate).
2. Programmatic Debugger Session Simulation (`PdbSessionAutomator`):
   - Initializes `pdb.Pdb(stdin=input_stream, stdout=output_stream)`.
   - Feeds scripted debugger command sequences into `stdin` via `io.StringIO`:
     * Navigation commands: `n` (step over), `s` (step into), `c` (continue).
     * Inspection commands: `p <var>` (print value), `pp <expr>` (pretty print), `whatis <var>`.
     * Stack navigation: `w` (where / stack trace display), `u` (up one stack frame), `d` (down one frame).
     * Breakpoints: `b <line_or_func>` (set breakpoint), `cl` (clear breakpoint).
   - Executes the targeted function under the control of the automator (`pdb.runcall(...)`).
   - Captures the exact interaction log from `stdout` to verify the state of inspected variables at each step.
3. Post-Mortem Crash Diagnosis (`diagnose_crash(func, *args, **kwargs) -> dict[str, Any]`):
   - Wraps function in a `try...except Exception:` block.
   - Upon encountering an uncaught crash, captures `sys.exc_info()[2]` (the traceback object).
   - Programmatically extracts the crash site frame: file name, line number, offending line source code, local variables dictionary at crash point, and call stack depth.

Sample Input:
automator = PdbSessionAutomator()

# 1. Scripted interactive commands: inspect variable 'rate', step twice, print 'total', continue
scripted_commands = "p rate\nn\nn\np total\nc\n"
session_log = automator.run_scripted_debug(calculate_compound_interest, 1000, 0.05, 3, commands=scripted_commands)

# 2. Crash Diagnosis on zero-division input
crash_report = automator.diagnose_crash(calculate_compound_interest, 1000, 0.05, 0, frequency=0)

Expected Output:
Scripted Debugger Session Log:
(Pdb) p rate
0.05
(Pdb) n
(Pdb) n
(Pdb) p total
1050.0
(Pdb) c
Crash Diagnosis Summary:
- Exception Type: ZeroDivisionError
- Failing Function: 'calculate_compound_interest'
- Faulting Expression: 'rate / frequency'
- Captured Local Variables at Crash: {'principal': 1000, 'rate': 0.05, 'frequency': 0}
- Stack Frame Depth: 3

Constraints & Edge Cases:
- Never invoke interactive `pdb.set_trace()` directly in unattended test scripts without redirecting `stdin`/`stdout`, as it will hang automated CI pipelines.
- Traceback references must be cleared after post-mortem extraction to avoid cyclic garbage collection leaks.
